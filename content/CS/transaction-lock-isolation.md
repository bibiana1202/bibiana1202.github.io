포인트 차감과 주문 생성을 하나의 작업으로 처리하려면 트랜잭션이 필요하다. 여기에 같은 잔액을 여러 요청이 동시에 사용하는 상황까지 고려하면 동시성 제어도 함께 설계해야 한다. 아래 SQL 설명은 MySQL/MariaDB의 **InnoDB 테이블**을 전제로 한다.

## 트랜잭션과 HTTP 요청은 항상 1:1일까?

트랜잭션은 DB 작업을 하나의 논리적인 단위로 다루는 경계다. 하나의 요청이 트랜잭션을 시작하는 설계는 흔하지만, 요청 하나가 여러 트랜잭션을 수행하거나 명시적인 트랜잭션 없이 조회할 수도 있다. 트랜잭션 경계는 애플리케이션과 DB 설정이 결정한다.

COMMIT은 변경을 확정하고 ROLLBACK은 해당 트랜잭션의 미확정 변경을 취소한다. 오류가 났다고 언제나 전체 트랜잭션이 자동 취소되는 것은 아니므로 오류 경로에서도 명시적인 정리를 해야 한다. 외부 API 호출이나 이미 전송한 메시지는 DB ROLLBACK으로 취소되지 않는다.

## ACID와 데이터 정합성

| 특성 | 의미 |
| --- | --- |
| Atomicity, 원자성 | 트랜잭션 변경을 모두 반영하거나 모두 취소하는 단위로 다룸 |
| Consistency, 일관성 | 정의한 제약조건과 업무 규칙에 맞는 유효한 상태를 유지함 |
| Isolation, 격리성 | 동시 실행 사이의 가시성과 간섭을 정해진 수준으로 제어함 |
| Durability, 지속성 | 커밋된 결과를 장애 이후에도 유지하도록 보장함 |

DB는 선언된 제약조건을 검사할 수 있지만, 선언하지 않은 업무 규칙까지 알아서 지켜 주지는 않는다. 격리 수준마다 허용하는 현상도 다르고, 실제 장애 시 지속성은 로그 기록과 저장장치 등 설정의 영향을 받는다.

## 요청마다 트랜잭션 하나를 만들면 충분할까?

잔액이 10,000이고 두 요청이 각각 7,000 사용을 시도한다고 하자.

```text
A: 잔액 10,000 조회
B: 잔액 10,000 조회
A: 사용 가능 판단
B: 사용 가능 판단
```

두 트랜잭션 모두 같은 과거 상태를 근거로 판단할 수 있다. 이후 `point = 3000`처럼 읽어 둔 값으로 덮어쓰면 한 차감이 사라지는 결과가 가능하다. 잔액 조건 없이 `point = point - 7000`을 두 번 실행하면 음수 잔액이 될 수도 있다. 실제 결과는 격리 수준, 제약조건, 쿼리 형태에 따라 달라진다.

즉, “요청 하나당 트랜잭션 하나”와 “충돌하는 작업을 안전하게 처리한다”는 별개다. 모든 요청을 한 줄로 세우는 대신 충돌하는 데이터와 업무 규칙에 맞춰 제어 범위를 정한다.

## SELECT ... FOR UPDATE로 읽고 수정하기

다음은 실행 순서를 설명하는 예시다. `users.id`는 기본 키이고 대상 행이 존재한다고 가정한다.

```sql
START TRANSACTION;

SELECT point
FROM users
WHERE id = 1
FOR UPDATE;

-- 애플리케이션에서 행 존재 여부와 point >= 7000을 확인한다.
-- 조건 불충족이면 ROLLBACK하고 아래 작업은 실행하지 않는다.
UPDATE users SET point = point - 7000 WHERE id = 1;
INSERT INTO orders(user_id, amount) VALUES (1, 7000);

COMMIT;
-- 중간 오류 경로에서는 ROLLBACK한다.
```

모든 구문은 **같은 DB 연결의 같은 트랜잭션**에서 수행해야 한다. 커넥션 풀에서 매번 다른 연결을 얻으면 이 경계가 깨진다. InnoDB에서 `FOR UPDATE`를 여러 구문에 걸친 보호로 쓰려면 명시적으로 트랜잭션을 시작하거나 autocommit을 적절히 제어해야 한다. [MariaDB FOR UPDATE 문서](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update)

경합하는 수정·잠금 읽기는 기다릴 수 있지만 일반적인 MVCC 조회까지 모두 막는다는 뜻은 아니다. 잠금 범위는 검색 인덱스와 조건, 격리 수준에 따라 레코드뿐 아니라 범위에도 걸릴 수 있다. [MySQL 잠금 읽기 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

단순한 잔액 차감은 조건부 UPDATE로 판단과 변경을 합칠 수도 있다.

```sql
UPDATE users
SET point = point - 7000
WHERE id = 1 AND point >= 7000;
```

이때도 변경된 행 수가 1인지 확인해야 한다. 0이면 사용자가 없거나 잔액 조건을 만족하지 않은 것이다. 주문 생성까지 함께 묶어야 한다면 같은 트랜잭션 안에서 변경 행 수 확인, 주문 생성, COMMIT을 수행하고 실패 시 ROLLBACK한다.

## Deadlock은 어떻게 생길까?

A가 데이터 1을 잠그고 데이터 2를 기다리는데, B가 데이터 2를 잠그고 데이터 1을 기다리면 서로 진행할 수 없다. 이것이 교착 상태다.

DB가 교착 상태를 감지해 한 트랜잭션을 중단할 수 있으므로 애플리케이션은 해당 오류를 처리해야 한다. 자원 획득 순서를 통일하고 트랜잭션을 짧게 유지하면 발생 가능성을 줄일 수 있다. 재시도한다면 실패한 구문만이 아니라 트랜잭션 전체를 제한적으로 재시도하고, 외부 부수 효과의 중복 여부도 고려한다.

## Isolation Level은 무엇을 바꿀까?

SQL 표준의 대표적인 구분은 다음과 같다. 실제 DBMS의 구현은 표보다 강한 보장을 제공할 수도 있다.

| 수준 | 표준에서 허용 가능한 대표 현상 |
| --- | --- |
| READ UNCOMMITTED | 다른 트랜잭션의 미커밋 변경을 읽는 dirty read |
| READ COMMITTED | 같은 행을 다시 읽을 때 값이 달라지는 non-repeatable read |
| REPEATABLE READ | 같은 조건을 다시 조회할 때 행 집합이 달라지는 phantom read |
| SERIALIZABLE | 성공한 트랜잭션들의 효과가 어떤 직렬 실행과 같도록 보장 |

표의 현상은 해당 수준에서 반드시 발생한다는 뜻이 아니다. 예를 들어 InnoDB REPEATABLE READ는 일관된 스냅샷 조회와 잠금 읽기의 동작을 구분해야 한다. “격리 수준 이름만 같으면 모든 DB에서 동일하다”거나 “SERIALIZABLE은 물리적으로 한 번에 하나만 실행한다”고 단정하면 안 된다. [InnoDB 격리 수준 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

## 짧게 설명하기

> 트랜잭션은 DB 작업을 하나의 단위로 묶고, 격리 수준과 잠금 등은 동시 실행 사이의 충돌을 제어한다. 정합성을 지키려면 업무 규칙을 명확히 하고 적절한 쿼리, 제약조건, 트랜잭션 범위와 오류 처리를 함께 설계해야 한다.
