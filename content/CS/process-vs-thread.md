프로세스와 스레드를 구분할 때는 **실행 단위와 메모리 공유 범위**를 함께 보면 이해하기 쉽다.

## 프로세스와 스레드의 차이

프로세스는 실행 중인 프로그램의 인스턴스다. 운영체제는 프로세스마다 독립적인 가상 주소 공간과 자원을 관리한다. 프로세스 사이의 데이터를 주고받으려면 소켓, 파이프, 공유 메모리 같은 프로세스 간 통신(IPC)이 필요하다. 따라서 “프로세스는 기본적으로 메모리가 독립적이다”는 설명은 맞지만, 명시적으로 공유 메모리를 사용할 수도 있다.

스레드는 프로세스 안의 실행 흐름이다. 일반적인 OS 스레드는 같은 프로세스의 주소 공간을 공유하면서 각자의 스택과 레지스터 상태를 갖는다. 힙과 전역 데이터는 공유할 수 있다. [Linux pthreads 문서](https://man7.org/linux/man-pages/man7/pthreads.7.html)

```text
프로세스 A                        프로세스 B
공유할 수 있는 힙·전역 데이터       별도의 주소 공간
  ├─ 스레드 1: 스택 1
  └─ 스레드 2: 스택 2
```

여기서 “각자의 스택”은 실행 상태를 구분한다는 뜻이다. 같은 주소 공간에 있으므로 스택 메모리가 다른 스레드의 접근으로부터 자동으로 보호되는 것은 아니다.

## 같은 데이터를 수정하면 어떤 일이 생길까?

카운터가 0이고 두 실행 흐름이 각각 1을 더한다고 가정하자. 아래는 읽기와 쓰기가 나뉘는 상황을 보여주는 개념적인 예다.

```text
A: counter를 읽음 → 0
B: counter를 읽음 → 0
A: 0 + 1을 저장 → 1
B: 0 + 1을 저장 → 1
```

두 번 증가시켰지만 결과는 1이다. 이런 식으로 **공유 상태에 대한 실행 순서에 따라 결과의 올바름이 달라지는 상황**을 경쟁 상태(race condition)라고 한다. 동시에 같은 CPU에서 실행되어야만 생기는 것은 아니다. 작업이 번갈아 끼어들어도 발생할 수 있다.

## Mutex와 Lock은 무엇을 보호할까?

Mutex는 임계 구역에 한 번에 하나의 실행 흐름만 들어가게 하는 상호 배제 수단이다. 위 예제에서는 쓰기만 잠그는 대신, 읽고 계산하고 쓰는 전체 구간을 보호해야 한다. 공유 상태를 다루는 모든 경로가 같은 동기화 규칙을 따라야 효과가 있다.

Lock은 더 넓은 용어다. 읽기/쓰기 락처럼 접근 방식에 따라 허용 범위가 다른 잠금도 있다. 잠금은 대기 비용을 만들고, 여러 자원을 서로 다른 순서로 잠그면 교착 상태가 생길 수 있다.

## Node.js에 적용할 때 주의할 점

일반 OS 스레드의 메모리 모델을 Node.js Worker에 그대로 대입하면 안 된다. Node.js의 `worker_threads`는 각 Worker가 별도의 JavaScript 실행 환경을 사용한다. 일반 JavaScript 객체가 자동으로 공유되는 것은 아니며, 메시지를 주고받거나 `SharedArrayBuffer`를 통해 메모리를 명시적으로 공유한다. [Node.js Worker 문서](https://nodejs.org/api/worker_threads.html)

또한 JavaScript 실행 스레드가 하나여도 `await` 전후로 요청이 섞이면 논리적인 경쟁 상태가 생길 수 있다. 예를 들어 두 요청이 DB에서 같은 잔액을 읽은 뒤 각자 차감할 수 있다. 이 경우에는 DB 트랜잭션과 동시성 제어를 함께 고려해야 한다.

## 짧게 설명하기

> 프로세스는 독립적인 주소 공간을 갖는 실행 중인 프로그램이고, 스레드는 그 안의 실행 흐름이다. 같은 프로세스의 스레드는 주소 공간을 공유하므로 공유 상태를 변경할 때 경쟁 상태가 발생할 수 있다. 필요한 임계 구역에 Mutex 등의 동기화 수단을 적용한다.
